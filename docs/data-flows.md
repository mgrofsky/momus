# Data flows: what leaves the machine

This page lists what Momus sends to parties other than your own targets, by design, and how to turn each flow off where that is possible. It covers the scanner (the scan container), the DNS lookups its tools make, the brain (the web application container) when the analyst is on, and the optional seeder (the DNS seeding container).

The scanner never sends anything to the brain over a network. The two exchange files only, through the `jobs` and `published` folders. Everything the scanner sends leaves through its egress firewall (`scanner/entrypoint.sh`), which allows public addresses, traffic on the container's own loopback interface (it never leaves the scanner container; Docker's embedded resolver at 127.0.0.11 is reached this way), DNS (port 53) to the resolvers Docker's own resolver forwards to (even a non-public one), IPv6 neighbor discovery to link-local and link-scope multicast addresses, and, in lab mode, the lab range. It rejects every other private, link-local, and non-global destination.

## Sent to third parties during a scan

A "domain" below is an apex domain in scope. "DNS-verified" means its DNS proof (a TXT record only your install can produce) passed at the start of the run.

| What | Where it goes | What it learns | When | How to turn it off |
|---|---|---|---|---|
| Passive subdomain enumeration (subfinder with `-all`, assetfinder) | The tools' public sources (certificate logs, search and DNS datasets) | Each DNS-verified domain | Phase 1 of a full or inventory run | There is no setting to turn this off. Lab runs skip enumeration. For a real scan, leaving the domain out of scope is the only way. |
| Certificate-transparency lookup | crt.sh (`https://crt.sh/?q=%.<domain>`) | Each DNS-verified domain | Phase 1 | There is no setting to turn this off. Lab runs skip it. |
| dnsrecon standard records (`-t std`) | The domain's own nameservers, asked directly | The domain, and which records the scanner asks for | Phase 1, only for a domain whose every nameserver address passes the address check | There is no setting to turn this off. Lab runs skip it. |
| Zone transfer attempt (`dig axfr`) | Each address of each of the domain's nameservers that passes the address check, asked directly | That the scanner asked for a full copy of the domain's zone | Phase 2, for each DNS-verified domain | There is no setting to turn this off. Lab runs skip it. A successful transfer is reported as a misconfiguration. |
| DNS proof check | The local resolver (to find each domain's nameservers and their addresses), then each nameserver address directly (TXT `_scan-verify.<domain>`, no recursion) | Each domain in scope | The start of every non-lab run, every `scope-sync` job, the start of every non-lab `version-watch` job (only domains that pass in that job are probed), and `approve.py verify` | Required for any non-lab scan; it cannot be turned off. The token in the record is derived from the scanner's install secret, which is never published and stays in the scanner's state folder (`$SCAN_ROOT/state`). In lab mode (`compose.lab.yaml`) a `scope-sync` job's questions go to an unused lab address and get no answer. |
| CNAME chain lookups for version watch | The local resolver (`dig ... A` with the full answer) | Each host version watch is about to probe (from the scan database, the watches' own hosts, and hosts carried from earlier results) that passed the DNS proof and the name gate | Every `version-watch` job, before any probe | There is no setting to turn this off: the lookup is what lets exclusions apply through CNAMEs. A host whose lookup fails is not probed. Names under a domain that did not pass the proof in that job, and excluded names, are never looked up. |
| Network names for addresses | Team Cymru whois (`whois.cymru.com:43`, one bulk session, no key) | Every public address of the hosts the run classified as live | Phase 5 (`scanner/pipeline/enrich.py`) | There is no setting to turn this off. Private addresses (including every lab address) are never sent; with none to send, no connection is made. |
| End-of-life data | endoflife.date API (`https://endoflife.date/api/<product>.json`). A redirect is refused, not followed, so the request goes to that host only | Only that a run happened: every run asks for the same fixed list of products in `scanner/config/eol_products.txt` (no host names) | Phase 5 (`scanner/pipeline/enrich.py`) | There is no setting to turn this off. On an internal lab network the lookup fails and is skipped ("endoflife.date unreachable, giving up"). |
| Public vulnerability feeds | EPSS (`epss.cyentia.com`) and CISA KEV (`www.cisa.gov`). These downloads follow HTTP redirects wherever they lead; the EPSS address redirects to its publisher's current host (`epss.empiricalsecurity.com`) | Only that a download happened (no scan data is sent) | Every ingest, at most once per day (cached under `data/epss` and `data/kev`) | There is no setting to turn this off for scan jobs. Lab jobs skip the download (`ingest.py --no-feeds`). Run by hand, `ingest.py --no-feeds` or `--offline` skips it. The newest cached copy is used if there is one. |
| Nuclei template updates | ProjectDiscovery's template release (GitHub) | That an update happened | Only an `update-templates` job | Do not submit one. Scans never update templates. |

Tool update checks: subfinder, dnsx, httpx, and nuclei each check for a newer release at start unless told not to. `scanner/recon.sh` passes `-duc` (disable update check) on the calls that enumerate, resolve, probe, and run templates; the check would go to ProjectDiscovery's update service (`api.pdtm.sh`). The calls that read each tool's version for the run manifest (`-version`) and the `update-templates` job's nuclei call do not pass `-duc`. The image's tools are fixed; a newer version comes only with a new image.

### subfinder's sources and keys

subfinder reads its provider configuration (the API keys for sources that need one) from `/home/scanner/.config/subfinder/provider-config.yaml` in the scanner image. The image ships no such file, so **no API keys ship**, and sources that need a key have none. (The only provider file in the image, `/home/scanner/.config/uncover/provider-config.yaml`, has every key list empty.) The scanner's root file system is read-only and `compose.yaml` mounts nothing at that path, so adding keys means mounting your own file there.

## DNS lookups made by the tools

Every name the scan resolves is asked of a resolver, and the resolver learns the name.

| Tool | Resolver it asks outside lab mode | In lab mode |
|---|---|---|
| dnsx (phase 2: host addresses and CNAMEs; each domain's MX, TXT, NS, CAA, and SOA records and its `_dmarc` record), httpx (phase 3), and nuclei (phase 8) | Each tool's own built-in list of public resolvers (for example 1.1.1.1 and 8.8.8.8), asked directly | The container's resolver (Docker's 127.0.0.11), passed with `-r` |
| Everything else that resolves a name (dig for the DNS proof, the zone transfer attempt, and version watch; curl for crt.sh; whatweb; wafw00f; sslscan; the Python lookups for Team Cymru, endoflife.date, EPSS, and KEV; the version watch probe) | The container's resolver (Docker's 127.0.0.11), which forwards questions about other names to the upstream resolvers Docker is configured with | The same. In lab mode it answers the lab names and forwards every other question to the lab's unused upstream address on the internal network, where nothing answers. |

There is no setting to change the resolvers. subfinder and assetfinder query their sources over HTTPS; they look up the source's own host name through the container's resolver.

## Sent to targets

Probes from httpx, whatweb, wafw00f, nmap (approved addresses only), sslscan, and nuclei, plus verify and triage follow-ups pinned to the finding's host, and the version watch's one `GET /` per host per scheme per run, plus at most three same-host redirects from each (headers only; see `docs/version-watch.md`). These are the scan itself, governed by the scope controls (name gate, address gate, tool flags, and egress firewall). A name under your domain can be hosted by someone else: a host whose CNAME or address points at a listed hosting or SaaS provider is classed `third_party` and still receives the HTTP probe, the fingerprinting, and nuclei's takeover, misconfiguration, and DNS templates, but no port scan.

## Sent to the model provider by the analyst (the brain)

Only when an AI model provider is configured (`MOMUS_ANALYST_PROVIDER`; the default is `none`, which sends nothing) and an admin has confirmed, on the Settings page, the statement of what is sent and to whom. Full details: `docs/analyst.md`.

| What | Where it goes | When | How to limit or turn it off |
|---|---|---|---|
| The analyst's requests: fixed instructions; the task (for chat, the question as typed); the tool calls of the run and their results: identifiers (finding keys, host names, and run ids), the IP addresses of your hosts (in every mode, metadata-only included), severities, scores, versions, counts, and fixed vocabulary values; text taken from scanned sites (finding titles, descriptions, stored evidence excerpts, page titles, server banners, certificate names, and DNS values) after best-effort redaction by the scanner's own redaction module; the reasons people typed for manual marks; and notes a person has accepted | The one provider configured: Anthropic (`api.anthropic.com`), OpenAI (`api.openai.com`), Google's Gemini API (`generativelanguage.googleapis.com`), or Amazon Bedrock (`bedrock-runtime.<region>.amazonaws.com`; the model check uses `bedrock.<region>.amazonaws.com`); through the proxy `MOMUS_ANALYST_PROXY` when it is set (no proxy from the environment is ever used, and no redirect is followed) | When a person asks for a brief or a chat answer, and for each new snapshot if `MOMUS_ANALYST_AUTO_BRIEF=1` (off by default). At most `MOMUS_ANALYST_MAX_STEPS` requests per run, one run at a time, within the token budgets | `MOMUS_ANALYST_METADATA_ONLY=1` sends no text taken from scanned sites, no accepted notes, and no reasons typed for marks (identifiers, IP addresses, severities, versions, counts, and vocabulary values only). `MOMUS_ANALYST_PROVIDER=none` turns the analyst off. The confirmation is asked again whenever the statement changes: the provider, its region, the model, the metadata-only or automatic-brief setting, or the proxy. |
| The provider's API key | The same provider, as its credential only | With each request | Never logged, stored in the database, shown, or put in an error message. |

The brain needs outbound HTTPS to the configured provider (and, for Bedrock without a key, to the AWS credential endpoints its credential chain uses), plus DNS through the container's resolver to find it. Nothing in the stack limits it to that: the brain's network (`brain_net` in `compose.yaml`) is an ordinary Docker bridge network, and Docker does not restrict a container's outbound destinations. To enforce "the provider only", add a firewall rule in front of the brain, or run an egress proxy and set `MOMUS_ANALYST_PROXY` to it. With the provider `none`, the brain makes no outbound connection. In lab mode it is on an internal network with no route out, and only the test providers work. A separate lab browser bridge joins that internal network and a host-facing bridge, and forwards local browser requests, including login data and cookies, to the brain. It has no mounted files or configured secrets and accepts only requests with a local browser Host header; its upstream is fixed to `brain:8080`. The bridge's own network has an outbound route, unlike the brain's.

## Sent by the seeder (optional; off unless the `seed` profile is used)

The seeder is a third container (`compose.yaml`, service `seeder`, Compose profile `seed`). A plain `docker compose up` never starts it; it runs only with `docker compose --profile seed run --rm seeder` (once) or `--profile seed up -d seeder` (on an interval, `SEED_INTERVAL_MINUTES`). With it unused, nothing in this section happens. It has its own network with ordinary outbound access (it must reach your DNS services, which may be on private addresses), no published port, and no route to the scanner or the brain. It contacts only the DNS services you configure, and looks up their host names (the PowerDNS address if given by name, and the AWS endpoints) through the container's resolver. A transfer server is usually the zone's own name server, which can be a host in scope, and the scanner's firewall and exclusions do not apply to the seeder. Nothing taken from an answer is ever contacted. Every source is off until set in `seed.env` (the `SEED_*` variables in `.env.example`); the seeder reads only `seed.env`, never `.env`.

| What | Where it goes | Credentials | When | How to turn it off |
|---|---|---|---|---|
| Route 53 listing: `ListHostedZones`, then `ListResourceRecordSets` for each public hosted zone that is a DNS-verified domain or under one (private zones and other zones are not read); with `SEED_ROUTE53_ROLE_ARN`, one `AssumeRole` first | AWS: Route 53 (`route53.amazonaws.com`) and, for the role, AWS STS in `SEED_ROUTE53_REGION` (default `us-east-1`) | The default AWS credential chain with the configuration file pointed at nothing: environment variables, a credentials file given as a Docker secret (`AWS_SHARED_CREDENTIALS_FILE`), or the container or instance role (on the AWS example host, the instance role; see `deploy/aws/README.md`). No profile, single sign-on, or credential cache is used. The credentials file is the operator's own and the SDK honors what it says, including a `credential_process` line, which would run inside the seeder container. The assumed role's credentials are kept in memory only. | Each seeder run, with `SEED_ROUTE53=1` | Leave `SEED_ROUTE53` empty. |
| Zone transfers (AXFR over TCP port 53, by the seeder's own small client: one question, size and time limits) | Each server in `SEED_AXFR`, given as an IP address (never looked up by name) | None (the server decides by your address) | Each seeder run | Leave `SEED_AXFR` empty. |
| PowerDNS API: `GET <url>/api/v1/servers/<server>/zones/<zone>.` | `SEED_PDNS_URL` (redirects are refused; no proxy from the environment is used) | The API key, read from a file (`SEED_PDNS_API_KEY_FILE`, normally the Docker secret `momus_seed_pdns_api_key`), sent as `X-API-Key` to that address only | Each seeder run, for the zones in `SEED_PDNS_ZONES` that are verified domains or under one | Leave `SEED_PDNS_URL` empty. |
| Zone files | Nothing is sent: files are read from `./seed-zones` (mounted read-only) | None | Each run, with `SEED_ZONE_FILES=1` | Leave `SEED_ZONE_FILES` empty. |

What it reads and writes: it can read three things only: the scanner's list of DNS-verified domains (`verified_domains.json` in the `seed_scope` volume, mounted read-only in the seeder; the scanner writes it whenever it publishes `scope_status.json`, and it holds the domain names only), its own settings (`seed.env` and its Docker secrets), and the zone-file folder (`./seed-zones`, read-only). It does not mount the scanner's `published` folder, so it cannot read snapshots, reports, or any other scan result. It seeds only the domains on that list. Route 53, zone transfer, and PowerDNS may each add names only under the zone they were asked for; names from zone files are kept when they are under any DNS-verified domain. The scanner's list also decides which Route 53 hosted zones the seeder lists, so give the seeder's AWS role access only to the zones meant to be seeded (on the AWS example host, `SeederHostedZoneIds` does this; see `deploy/aws/README.md`). It writes only to the `seed` volume: `seed_hosts.txt` (host names, one per line, sorted; no addresses, record values, or source details) and `status.json` (time, names per source, fixed-text error codes, and the sources that failed). If a run finds nothing, an earlier `seed_hosts.txt` stays. Credentials, exception messages, and DNS answer text are never logged or written there: an unusual name or answer is dropped or becomes a fixed error code for its source, and the log holds fixed lines only, never a traceback. The scanner mounts the volume read-only and treats the file as untrusted input (`scanner/pipeline/seed_input.py`: no symlink, size and line caps, host-name lines only), then passes every name through its name gate; the run manifest records how many were read and how many passed. The brain does not mount the volume. The seeder does not read cloud resource inventories (load balancers, distributions, accelerators): that would need broad read permissions.

## Never sent

- Scan results, evidence, or the scan database, except what the analyst sends to the model provider you configure (above): they stay in the scanner's volumes, the `published` folder, and the brain.
- Proxy settings are cleared before any scan tool runs (the scanner's entrypoint starts the runner with a clean environment), so no scan tool is routed through a proxy from the environment. The brain removes the proxy, trust-store, and SDK variables from its own environment at start-up and builds its provider clients without trusting the environment; its only proxy is `MOMUS_ANALYST_PROXY` (see `docs/analyst.md`).
